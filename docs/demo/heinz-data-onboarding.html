How Heinz's data gets into Compliance Hub

Heinz keeps product, packaging and sales data in several systems (SAP, Snowflake, Trace One, supplier files). We do not replace any of them. We connect once, map their columns to our data points, check what is missing or wrong, and send the fixes back to the system that owns the data.

The idea

Collect once, check, reuse everywhere

Every value we store remembers where it came from (erp, plm, csv, manual, estimate, correction) and which data point (DP01, DP02 …) it answers. EPR, PPWR, DPP and hotspots all read the same record.

Connecting

Three ways data reaches us

All three end in the same import pipeline (draft → mapping → preview → approve), so the rest of the platform does not care how the data came in.

Warehouse view

To build
Snowflake. Our recommended first choice for Heinz.
  • Heinz creates a schema with three views: products, components, sales
  • They give us a service user with a read-only role on that schema only, key-pair login
  • We run SELECT on the views; each view has an UPDATED_AT column so later syncs pull only changed rows
  • Heinz controls exactly what we see; nothing else in their warehouse is exposed

System API

Simulated today
SAP OData, Trace One API. When the data is not in Snowflake.
  • Technical user with read-only permission on the needed objects
  • We pull only the fields whose data point comes from that system
  • Credentials stored encrypted per workspace, never in the browser
  • In the demo, SAP and Trace One syncs are simulated with sample data

File or vendor form

Live in app
CSV extracts, supplier declarations, one-off data.
  • Upload on Data collection → Import
  • A file with the same columns as an earlier one reuses its mapping
  • Suppliers fill our vendor template; today we import it, a supplier link is to build
  • Also the fallback while IT access is pending
Why the view, not raw tables. If Heinz builds views with the column names we agree, our mapping is almost one-to-one and their internal table changes do not break our sync. It is also the easiest thing for their security team to approve: read-only, one schema, no write access.
First load

How we read and map their data the first time

DraftRows arrive and are stored as an import batch. Nothing touches products yet.
MappingEach column is matched to a field. We suggest from names ("EAN" → GTIN); a person confirms.
PreviewShows new and updated products, rejected rows and warnings before anything is saved.
ApproveA background job writes the rows. The mapping is saved for next time.
ResultProducts, components and sales appear; gaps and fees update at once.

Ongoing

What happens on every sync after the first

The source remembers its last approved mapping, so a sync maps itself. With auto-approve on, a sync with no rejected rows imports straight away; otherwise it waits in Data collection for a person to approve. Every sync is kept in the sync history.

How rows are matched

  • Products by SKU; a new SKU creates a product
  • Components by the system's component ID, then by name; otherwise added
  • Sales lines by their ID; otherwise added
  • Nothing is deleted by a sync; removals are done on the product page

How values are merged

  • Incoming value present → it replaces what we had, even a manual edit or an estimate
  • Incoming value empty, we have one → we keep ours; an empty cell never wipes data
  • Both empty → stored as missing, which becomes a gap
  • Gap decisions (requested, accepted) survive re-syncs
The source system wins. This is deliberate: SAP and Trace One stay the single source of truth. A correction made only in our platform is overwritten by the next sync if SAP still has the old value. That is why every correction goes back to the source (see Validation).
Demo step 3

How gaps are found and fixed

A gap is a value a rule says is missing or not good enough. The rule library runs over every product on every read, filtered to Heinz's modules and countries. So a gap appears the moment data is missing and disappears by itself when a sync brings a valid value.

KindExampleHow it is filledWho
EstimableWeight of a cap missing in PLMAverage of components of the same material and packaging level (similar_average); marked Estimated until real data arrivesMonk Spaces proposes, Heinz accepts
EstimableRecycled content not declaredFixed value, e.g. 0% (fixed), the safe assumption for feesMonk Spaces proposes, Heinz accepts
Needs dataPFAS declaration, recycled-content certificateRequest from supplier; gap shows as requested until the vendor file comes inHeinz procurement → supplier
Needs dataGTIN, DoC signatory, EU labelFixed at the source (SAP) or entered on the product pageHeinz data owner

Each gap also has a phase from horizon scanning: due now (rule in force), collecting (inside the lead time, 3 months by default) or upcoming. Due gaps are listed first, so Heinz works on what matters for the next deadline.

Checklist

What we ask Heinz IT for

  • List of systems holding product, packaging, sales and supplier data
  • Agreed SKU key, and a cross-reference if systems differ
  • Snowflake: schema with products, components and sales views
  • Snowflake: service user, read-only role, key-pair login
  • An UPDATED_AT column on each view
  • SAP / Trace One API user, read-only, if not in Snowflake
  • Network allowlist for our server IPs, if they restrict access
  • Sample CSV of the pilot SKUs while access is pending
  • Data owner per system for corrections
  • Their security questionnaire and data processing agreement
